## Q1. Que frameworks de backtesting se adequam ao bot (URL, actividade, licença, curva de aprendizagem, replay event-driven com LLM por barra, caching)

### Takeaway
Para um bot de poucas acções US a 1 min com decisões lentas de um LLM, os candidatos realistas são três: `vectorbt` (vectorizado, ideal para reproduzir sinais já gravados), `backtesting.py` (event-driven minimalista com `sl/tp` que imita bracket orders) e `nautilus_trader` (event-driven de produção, mesmo código em backtest e live, adaptador Interactive Brokers, mas curva íngreme). `backtrader` está funcionalmente parado, `zipline-reloaded`/`Lean`/`Qlib` são pesados ou orientados a carteiras/factores, e `freqtrade`/`Jesse` só suportam cripto. Nenhum framework tem suporte nativo para "chamar um LLM por barra com cache"; isso tem de ser feito pelo utilizador (tabela de cache em SQLite indexada por hash do prompt) — ver Inferências.

### Cited Findings
- **vectorbt** (https://github.com/polakowo/vectorbt): 9.3k estrelas; licença "Apache 2.0 with Commons Clause" (modelo fair-code: uso gratuito para indivíduos e organizações, proibido vender produtos/serviços que sejam primariamente este software); representa preços/sinais/posições como arrays NumPy compilados com Numba; API para sinais externos `Portfolio.from_signals()`, `Portfolio.from_orders()`, `Portfolio.from_holding()`, `Portfolio.from_random_signals()`; `stats()` devolve total return, drawdown, win rate, profit factor, Sharpe, Sortino, Calmar, Omega; a edição open-source é complementada pela comercial **vectorbt PRO** (paralelização, +100 funcionalidades, actualizações semanais) — [GitHub polakowo/vectorbt](https://github.com/polakowo/vectorbt).
- vectorbt "reframes backtesting as an array problem … compiling hot loops with Numba to run at near-C speed"; é optimizado para testar milhares de estratégias de uma vez, enquanto backtrader corre evento a evento e é muito mais lento em escala — [AlgoLab comparison 2026](https://algolab.co.kr/blog/python-backtesting-library-comparison-2026) (fonte secundária, blog).
- A documentação de métricas do vectorbt inclui módulo `returns/metrics` (aparece em pesquisa associado a Deflated Sharpe) — [vectorbt.dev/api/returns/metrics](https://vectorbt.dev/api/returns/metrics) (não foi possível abrir a página; apenas o título do resultado).
- **backtesting.py** (https://github.com/kernc/backtesting.py): ~9k estrelas; licença **AGPL-3.0**; 461 commits, CI activo, 50 issues abertas (activo em 2024-2026); método `Strategy.next()` executado por candela (event-driven); `sl`/`tp` em ordens dão funcionalidade de bracket; estatísticas incluem "Sharpe Ratio", "Sortino Ratio", "Calmar Ratio", "Max. Drawdown", "Win Rate", "Profit Factor", "Expectancy", "SQN"; optimizador SAMBO; limitação: um só instrumento por backtest e historicamente sem fracções de acção — [GitHub kernc/backtesting.py](https://github.com/kernc/backtesting.py).
- "Backtesting.py has the simplest event API and produces first results in half a day, but is focused on single stocks"; não tem live trading nem integração com broker — [AlgoLab 2026](https://algolab.co.kr/blog/python-backtesting-library-comparison-2026).
- **nautilus_trader** (https://github.com/nautechsystems/nautilus_trader): 29.6k estrelas; licença **LGPL-3.0**; núcleo Rust (mimalloc, tokio) com Python como "control plane"; "The same strategy and execution-algorithm code can run across backtest and live systems"; motor event-driven determinístico com resolução de nanossegundos; adaptadores incluem **Interactive Brokers**, Binance, Coinbase, Kraken, OKX, Bybit, dYdX, Hyperliquid, Betfair, Polymarket; Python 3.12–3.14; releases estáveis no PyPI com cadência quinzenal — [GitHub nautechsystems/nautilus_trader](https://github.com/nautechsystems/nautilus_trader).
- nautilus_trader v1.222.0 (Jan 2026) introduziu serialização Cap'n Proto como alternativa ao MessagePack para replay de tick data com milhões de eventos; "steep learning curve with complex order state models" — [AlgoLab 2026](https://algolab.co.kr/blog/python-backtesting-library-comparison-2026); integração Databento documentada em [nautilustrader.io/docs/latest/integrations/databento](https://nautilustrader.io/docs/latest/integrations/databento).
- **backtrader** (https://github.com/mementum/backtrader): 23.4k estrelas; licença **GPL-3.0**; "Python >= 3.2", Cerebro event-driven, `buy_bracket`, analisadores SharpeRatio/DrawDown/TradeAnalyzer/SQN, live trading IB via IbPy, 122 indicadores — [GitHub mementum/backtrader](https://github.com/mementum/backtrader). Segundo fonte secundária, "has been effectively unmaintained for several years and fails to install cleanly on Python 3.10+ without patching" — [AlgoLab 2026](https://algolab.co.kr/blog/python-backtesting-library-comparison-2026).

- **QuantConnect Lean** (https://github.com/QuantConnect/Lean): 21.9k estrelas; **Apache-2.0**; C# e Python; execução local via `pip install lean` + `lean backtest`/`lean live` ou Docker; build local exige dotnet 10 SDK; pasta `/Brokerages` com integrações; a página não especifica se há dados de minuto de acções US gratuitos localmente — [GitHub QuantConnect/Lean](https://github.com/QuantConnect/Lean).

- **freqtrade** (https://github.com/freqtrade/freqtrade): 55k+ estrelas; Python 3.11+; suporta **exclusivamente exchanges de criptomoedas** (spot/futuros via CCXT); backtesting, hyperopt, dry-run, e **FreqAI** ("self-trains to the market via adaptive machine learning methods") — [GitHub freqtrade/freqtrade](https://github.com/freqtrade/freqtrade).

### Inferences
- Encaixe com o bot: `vectorbt` é a via mais barata para transformar o log SQLite (BUY/SELL/HOLD + preço por minuto) em séries `entries`/`exits` e obter curva de capital, drawdown e estatísticas de trades sem reescrever lógica; `backtesting.py` é a escolha se se quiser um loop por barra fiel ao bot (brackets via `sl`/`tp`) para um único ticker; `nautilus_trader` só compensa se o objectivo for migrar a execução live para o mesmo motor (tem adaptador IB), aceitando semanas de aprendizagem.
- Nenhum dos frameworks oferece "cache de decisões de LLM"; mas como todos são loops Python por barra (backtesting.py, backtrader, nautilus) ou aceitam sinais pré-computados (vectorbt), o padrão natural é: (a) uma tabela `decisions_cache(prompt_hash, symbol, bar_ts, action, confidence, model, raw_json)` em SQLite; (b) a função de decisão consulta primeiro a cache; (c) o replay histórico corre uma vez a chamar o Ollama (lento) e as iterações seguintes de análise são instantâneas. Isto é inferência a partir das APIs descritas, não funcionalidade documentada.
- Custo de LLM por barra: 390 barras/dia × N acções × segundos por chamada local torna inviável um ano de replay; a inferência prática é só pedir decisão ao LLM nas barras onde um gatilho barato (indicador) dispara, ou amostrar barras, e registar isso como parte do protocolo.
- Licenças: AGPL-3.0 (backtesting.py) e GPL-3.0 (backtrader) só importam se o código for distribuído; para uso local são irrelevantes. vectorbt (Commons Clause) impede revender o software, não o uso interno.

### Gaps
- Não foi possível confirmar a data do último commit/release de vectorbt open-source, backtesting.py, backtrader e zipline-reloaded (as páginas GitHub lidas não mostravam datas no excerto; a API do GitHub estava bloqueada para esta sessão).
- A afirmação de que backtrader "não instala em Python 3.10+ sem patch" vem de um blog (AlgoLab), não de uma fonte primária.

## Q2. Qual a forma mais leve de reproduzir o log SQLite do bot e calcular expectancy / Brier / drawdown sem reescrever tudo

### Takeaway
A via mais leve não é um framework de backtesting: é (1) pandas sobre o log SQLite para rotular cada decisão com o retorno forward (já existe a retrospectiva de 30 min), (2) `quantstats` sobre a série de retornos resultante para Sharpe/Sortino/drawdown/profit factor/Kelly/risk of ruin e relatório HTML, e (3) `vectorbt.Portfolio.from_signals` quando se quiser simular posições, custos e brackets a partir dos sinais gravados. Brier/ECE/reliability calculam-se com `scikit-learn` (`brier_score_loss`, `calibration_curve`) ou NumPy puro.

### Cited Findings
- `quantstats` opera sobre "pandas Series of returns" (diárias, semanais ou mensais), não sobre trades discretos; módulos `qs.stats` (Sharpe, Sortino, Calmar, max drawdown, CAGR, volatilidade, VaR/CVaR, win rate, profit factor, consecutive wins/losses, Kelly criterion, **risk of ruin**, information ratio), `qs.plots` (incl. Monte Carlo), `qs.reports.html()`; `qs.extend_pandas()` adiciona os métodos às Series; Monte Carlo com probabilidades de "bust/goal"; Python >= 3.10; licença Apache 2.0; nota explícita: "Period-based metrics (win rate, consecutive wins) reflect return periods, not discrete trades" — [GitHub ranaroussi/quantstats](https://github.com/ranaroussi/quantstats).
- vectorbt: `Portfolio.from_signals()` faz backtest de entradas e saídas; `Portfolio.from_orders()` a partir de ordens; `stats()` devolve total return, drawdown, win rate, profit factor, Sharpe, Sortino, Calmar, Omega — [GitHub polakowo/vectorbt](https://github.com/polakowo/vectorbt).
- backtesting.py devolve "Expectancy", "Profit Factor", "SQN", "Win Rate", "Max. Drawdown", Sharpe/Sortino/Calmar como pandas Series — [GitHub kernc/backtesting.py](https://github.com/kernc/backtesting.py).
- Definições de calibração usadas na prática: o Brier Score "measures the squared error between a predicted probability vector and the one-hot encoded true label", menor é melhor; um reliability diagram agrupa previsões por confiança e traça confiança média (x) contra frequência empírica de positivos (y), modelo perfeito segue a diagonal; ECE é "the bucketed gap between predicted probability and observed frequency", ponderado pelo tamanho do bin — [MetricGate: Brier vs Log Loss vs Calibration](https://metricgate.com/blogs/brier-score-vs-log-loss-vs-calibration/); [MetricGate reliability diagram](https://metricgate.com/calculator/reliability-diagram-calibration/).
- Fórmula de risk of ruin em forma fechada mais citada: `risk_of_ruin = ((1 - Edge) / (1 + Edge)) ^ Capital_Units`, assumindo ganhos e perdas iguais, apostas fixas e independência — [Traders Second Brain: risk of ruin math](https://traderssecondbrain.com/guides/risk-of-ruin-math) (fonte secundária; a origem é Ralph Vince, *Portfolio Management Formulas*).
- Monte Carlo de trades: "reshuffles [trade results] thousands of times" para obter distribuição de drawdowns e probabilidade de ruína; "the analytical formula systematically underestimates risk of ruin because it ignores the actual consecutive loss sequences" — [Backtrex: Monte Carlo risk of ruin](https://backtrex.com/en/blog/monte-carlo-risk-of-ruin-trading-backtest); [Backtrex: Monte Carlo guide](https://backtrex.com/en/blog/monte-carlo-simulation-trading).

### Inferences
- Pipeline mínimo (inferido das APIs acima): `SELECT ts, symbol, action, confidence, price FROM decisions` → juntar o preço 30 min depois (ou usar a coluna já produzida pela retrospectiva) → `y = 1` se a direcção escolhida foi lucrativa (BUY e preço subiu; SELL e preço desceu; para HOLD usar |retorno| < limiar) → `p = confidence/100` → `brier = mean((p - y)**2)`; `hit_rate = mean(y)`; `expectancy = p_win*avg_win - (1-p_win)*avg_loss`; `profit_factor = soma dos ganhos / soma das perdas`; agregar P&L por dia e passar a `qs.reports.html(returns, benchmark='SPY')`.
- Para o Brier é preciso um baseline: Brier da previsão constante `p = taxa base` (climatologia) e Brier de confiança aleatória; só um Brier abaixo do baseline climatológico significa que a confiança do LLM tem informação.
- quantstats usa retornos por período, não por trade; para estatísticas por trade (expectancy, SQN, win rate de trades) é preferível o `stats()` de vectorbt/backtesting.py ou cálculo directo em pandas.

### Gaps
- Não foi encontrada documentação (acessível nesta sessão) de uma biblioteca Python que combine, num só pacote, replay de log de decisões + métricas de calibração + métricas de trading; a combinação pandas + sklearn + quantstats/vectorbt é a solução prática.

## Q3. Metodologia de validação: walk-forward, OOS, shadow/paper, baselines aleatórios, expectancy, profit factor, Sharpe/Sortino, drawdown, Monte Carlo, risk of ruin, tamanho mínimo de amostra

### Takeaway
Os textos de referência convergem: separar sempre in-sample/out-of-sample com janelas walk-forward (Pardo: eficiência WFE = OOS/IS, > 0,5 aceitável, < 0,3 alarme), comparar com baselines aleatórios/permutados, não confiar em menos de ~100-200 trades, e reportar métricas robustas a não-normalidade (PSR/DSR) em vez de um Sharpe cru. Em modo paper o scoring diferido a 30 min já implementado é exactamente um "shadow score"; falta-lhe o teste contra o acaso e correcção por múltiplas tentativas.

### Cited Findings
- Walk-Forward Efficiency: `WFE = (Annualized OOS Performance) / (Annualized IS Performance)`; regras de Pardo: WFE > 0,5 sugere robustez, WFE ≈ 1 ideal, WFE < 0,3 é sinal de sobreajuste — [MQL5: Walk-Forward Efficiency Ratio](https://www.mql5.com/en/articles/23250); [quantammsim: Walk-Forward Analysis](https://quantammsim.readthedocs.io/en/latest/tutorials/walk_forward_analysis.html); Pardo (2008) citado em [AlgoAdvantage podcast com Bob Pardo](https://algoadvantage.substack.com/p/035-bob-pardo-ii-building-trading).
- Teste binomial de win rate contra moeda ao ar: "a 65% win rate over 20 trades is NOT statistically significant, but 65% over 200 trades IS"; t-stat de retornos por trade < ~2 não distingue de ausência de edge; fórmula de Cochran para amostra mínima `n = Z^2 · p · q / e^2`; Mark Douglas sugere 20 amostras, mas "approximately 200 trades" para "reasonable confidence" e, estatisticamente, "hundreds if not thousands" — [RB Trading: The 200-Trade Rule](https://rbtrading.substack.com/p/the-200-trade-rule-why-most-traders); [StrategyQuant forum](https://strategyquant.com/forum/topic/what-is-your-minimum-number-of-trades-per-year/); [LuxAlgo: Significance of Returns](https://www.luxalgo.com/library/concept/significance-of-returns.md) (fontes de praticantes, não académicas).
- Framework académico recente de validação walk-forward para sinais de microestrutura (hipóteses interpretáveis, walk-forward rigoroso) — [arXiv 2512.12924](https://arxiv.org/pdf/2512.12924) (apenas título/resumo via pesquisa; PDF bloqueado).
- Monte Carlo: reordenar o histórico de trades milhares de vezes dá "probability of ruin, the range of expected drawdowns, and the confidence intervals around your returns"; profissionais visam probabilidade de ruína < 5 %, < 1 % excelente — [Backtrex](https://backtrex.com/en/blog/probability-of-ruin-trading-monte-carlo); [TradeZella Monte Carlo](https://www.tradezella.com/blog/monte-carlo-simulation-for-trading-stress-test-any-strategy-before-you-risk-real-capital).
- Risk of ruin depende de win rate, rácio ganho/perda médio (R-múltiplo) e % de capital arriscado por trade; "doubling risk per trade roughly quadruples ruin probability for traders near break-even" — [LuxAlgo: Risk of Ruin](https://www.luxalgo.com/library/concept/risk-of-ruin.md); [Traders Second Brain](https://traderssecondbrain.com/guides/risk-of-ruin-math).
- Jesse documenta "Monte Carlo analysis for stress-testing strategies" e "Rule Significance Testing to validate entry rules" como funcionalidades de backtest — [GitHub jesse-ai/jesse](https://github.com/jesse-ai/jesse).
- quantstats inclui `risk_of_ruin`, `kelly`, Monte Carlo com probabilidade de bust/goal — [GitHub ranaroussi/quantstats](https://github.com/ranaroussi/quantstats).
- "The Alpha Illusion" propõe testes estruturais obrigatórios antes de aceitar retornos de agentes LLM: "temporal integrity, real-world frictions, counterfactual robustness, predictive calibration, numerical execution, and multi-agent disaggregation", e um protocolo mínimo de reporte P1–P6 — [alphaxiv 2605.16895](https://www.alphaxiv.org/abs/2605.16895).

### Inferences
- Baseline aleatório adequado ao bot: (i) permutar os rótulos y mantendo as acções (teste de permutação do hit-rate), (ii) política aleatória com a mesma proporção BUY/SELL/HOLD avaliada nas mesmas barras, (iii) `Portfolio.from_random_signals` do vectorbt com o mesmo número de entradas para obter a distribuição de Sharpe "sem skill". O hit-rate do LLM só é evidência se cair fora do percentil 95 dessas distribuições.
- Com 1 minuto e decisões a cada barra, 200 decisões acumulam-se num dia; mas decisões em barras consecutivas são fortemente correlacionadas (mesma tendência), por isso o "n efectivo" é muito menor — contar trades fechados (brackets) ou decisões espaçadas ≥ 30 min, não barras.
- Shadow/paper scoring: o scoring a 30 min já é um rótulo OOS genuíno (sem look-ahead), desde que o LLM não veja barras futuras; o que falta é persistir a confiança calibrada e correr semanalmente Brier, ECE, hit-rate vs. permutação e PSR sobre esses rótulos.

### Gaps
- Não foi possível aceder ao texto de Pardo (*The Evaluation and Optimization of Trading Strategies*) nem ao de López de Prado (*Advances in Financial Machine Learning*); os limiares de WFE e as recomendações de amostra vêm de fontes secundárias que os citam.
- Não se encontrou um limiar de "n mínimo de trades" com base académica forte; os números 20/100/200 são regras de praticantes.

## Q4. Como avaliar calibração da confiança de um sinal tipo classificador (reliability diagrams, Brier, ECE) e condicionar execução por probabilidade calibrada

### Takeaway
A prática é tratar a confiança verbalizada do LLM como uma pontuação a calibrar, não como probabilidade: medir Brier e ECE com reliability diagram, ajustar uma função de calibração (Platt/sigmoid com poucos dados, isotónica com muitos) em dados de calibração separados, e só executar quando a probabilidade calibrada ultrapassa o limiar de break-even dado o rácio TP/SL do bracket. A literatura sobre LLMs mostra que a confiança verbalizada é muitas vezes sobreconfiante e inconsistente entre modelos.

### Cited Findings
- Reliability diagram: bins por confiança, x = confiança média, y = frequência empírica; ECE "is an L1 calibration error, weighted by bin size"; expõe sobreconfiança (previsto > observado) ou subconfiança por bucket; "ECE near 0 indicates good calibration; values above 0.05 suggest meaningful miscalibration" — [MetricGate reliability diagram](https://metricgate.com/calculator/reliability-diagram-calibration/); [MetricGate Brier vs Log Loss](https://metricgate.com/blogs/brier-score-vs-log-loss-vs-calibration/).
- Uso em trading: "if the curve shows 90 percent predictions winning only 60 percent of the time, thresholds and stake sizes built on the raw probabilities are wrong and need recalibration first"; "A miscalibrated 80 percent is fine for ranking setups but dangerous when fed into position sizing" — [LuxAlgo: Probability Calibration Curves](https://www.luxalgo.com/library/concept/probability-calibration-curves.md) (fonte comercial/educativa).
- scikit-learn: "Sigmoid calibration is preferable in cases where the calibration curve is sigmoid and where there is limited calibration data, while isotonic calibration is preferable for non-sigmoid calibration curves and in situations where large amounts of data are available"; a isotónica "makes no such strong assumptions and can deal with either shape, provided that there is sufficient calibration data" — [scikit-learn: Probability Calibration curves (exemplo)](https://scikit-learn.org/0.24/auto_examples/calibration/plot_calibration_curve.html); [scikit-learn 1.16 Probability calibration](https://scikit-learn.org/0.18/modules/calibration.html) (versões antigas indexadas; a página actual estava bloqueada).
- LLMs: "Just Ask for Calibration" (Tian et al., EMNLP 2023) mostra que em vários RLHF-LMs a confiança verbalizada é frequentemente melhor calibrada que as log-probabilidades, com ECE tão baixo como 0,07 com prompting adequado; mas outros trabalhos argumentam o contrário ("verbalized confidence scores are poorly calibrated") e que modelos RLHF "consistently assign higher confidence scores than SFT-only counterparts, and those scores don't correlate better with accuracy" — [ACL Anthology 2023.emnlp-main.330](https://preview.aclanthology.org/naacl24-info/2023.emnlp-main.330); [ar5iv 2305.14975](https://ar5iv.labs.arxiv.org/html/2305.14975); [Tian Pan: LLM calibration in production](https://tianpan.co/blog/2026-04-20-llm-calibration-production-overconfidence) (blog).
- "The Alpha Illusion" formula a mesma ideia para trading: "Language confidence is not tradable probability, narrative reasoning is not numerical execution"; propõe usar LLMs "as auditable information interfaces upstream of independent calibration, risk, and execution modules" — [alphaxiv 2605.16895](https://www.alphaxiv.org/abs/2605.16895).

### Inferences
- Gating por break-even (inferência aritmética padrão): com bracket TP = a·R e SL = R, a probabilidade mínima de acerto para expectancy ≥ 0 é `p* = 1/(1+a)` (ex.: TP/SL = 1,5 → p* = 40 %; 1:1 → 50 %), a somar custos/slippage; executar apenas se `p_calibrada(confidence, regime) > p* + margem`.
- Com poucas centenas de decisões rotuladas, usar Platt/sigmoid (ou simplesmente a tabela de bins do reliability diagram como mapa confiança→frequência observada); passar a isotónica só com milhares de rótulos. Recalibrar por janela deslizante (walk-forward) porque a calibração do LLM muda com o regime e com a versão do modelo Ollama.
- Também vale medir a "resolução": se o hit-rate é igual em todos os bins de confiança, a confiança não tem valor discriminativo mesmo que o Brier pareça aceitável — comparar com o Brier da taxa base.

### Gaps
- Não se encontraram estudos publicados que meçam Brier/ECE de confianças verbalizadas de LLMs locais (Llama/Qwen via Ollama) em decisões intradiárias de acções; a evidência de calibração de LLMs vem de QA/factualidade.

## Q5. Tamanhos de amostra e testes estatísticos recomendados por referências quant antes de escalar risco (Pardo, López de Prado/Bailey: PSR, MinTRL, DSR, MinBTL, PBO)

### Takeaway
Bailey & López de Prado fornecem as ferramentas formais: o Probabilistic Sharpe Ratio dá a probabilidade de o Sharpe verdadeiro exceder um limiar dado T observações, assimetria e curtose; o Minimum Track Record Length dá o T necessário; o Deflated Sharpe Ratio sobe o limiar para o Sharpe máximo esperado de N tentativas sem skill; e o Minimum Backtest Length aproxima-se por `2·ln(N)/E[max SR]^2`. Para um bot LLM, cada prompt/modelo/limiar de confiança experimentado conta como tentativa N.

### Cited Findings
- PSR (López de Prado, 2012): `PSR(SR*) = Φ( (SR̂ − SR*) / σ̂(SR̂) )`; o erro-padrão do Sharpe depende do tamanho da amostra e de assimetria e curtose; estratégias com assimetria negativa ou caudas pesadas "require much longer track records"; **MinTRL** é o menor número de observações para o Sharpe medido ser significativo a dado nível de confiança, e "can easily exceed several years of monthly data" — [TradingStrategy.ai: Probabilistic Sharpe ratio](https://tradingstrategy.ai/glossary/probabilistic-sharpe-ratio).
- DSR (Bailey & López de Prado, *Journal of Portfolio Management* 40(5), 2014): corrige "Selection bias under multiple testing and non-Normally distributed returns" — [SSRN 2460551](https://papers.ssrn.com/abstract=2460551) (apenas título/resumo via pesquisa).
- Fórmula do Sharpe máximo esperado: `SR* = sqrt(V) · ((1 − γ) · Φ⁻¹(1 − 1/N) + γ · Φ⁻¹(1 − 1/(N·e)))`, com V = variância dos Sharpe entre tentativas, γ ≈ 0,5772 (Euler-Mascheroni), N = número de tentativas efectivamente independentes; e `DSR = PSR(SR*) = Φ( (SR̂ − SR*) · sqrt(T − 1) / sqrt(1 − γ3·SR̂ + ((γ4 − 1)/4)·SR̂²) )` com γ3 = assimetria, γ4 = curtose — [Wikipedia: Deflated Sharpe ratio](https://en.wikipedia.org/wiki/Deflated_Sharpe_ratio); [LuxAlgo: Deflated Sharpe Ratio](https://www.luxalgo.com/library/concept/deflated-sharpe-ratio.md); implementação Python em [fynance.research.deflated_sharpe_ratio](https://fynance.readthedocs.io/en/latest/generated/fynance.research.deflated_sharpe_ratio.html).
- MinBTL (Bailey, Borwein, López de Prado, Zhu, "Pseudo-Mathematics and Financial Charlatanism", 2014): limite superior `MinBTL ≈ 2 · ln(N) / (E[max SR])²` — necessário para evitar escolher, entre N estratégias independentes, a de maior Sharpe in-sample cujo Sharpe out-of-sample esperado é zero — [qf-lib: backtest_overfitting_sheet (código)](https://qf-lib.readthedocs.io/en/v2.2/_modules/qf_lib/analysis/backtests_overfitting/backtest_overfitting_sheet.html); [CXO Advisory resumo](https://www.cxoadvisory.com/?p=23736); PDF em [carmamaths.org/jon/BODT.pdf](https://carmamaths.org/jon/BODT.pdf) (não aberto).
- Probability of Backtest Overfitting (PBO) via CSCV (Bailey, Borwein, López de Prado, Zhu) — [SSRN 2326253](https://papers.ssrn.com/abstract=2326253) (título apenas).
- Papel recente que aplica DSR/MinBTL a estratégias FX autónomas: "Is it a great Autonomous FX Trading Strategy or you are just fooling yourself" — [arXiv 2101.07217](https://arxiv.org/pdf/2101.07217) (título apenas).
- Em descoberta de estratégias por LLM com correcção search-aware, "every LLM-discovered strategy tested … fails certification against the agent's own recorded trial count", enquanto prémios de risco passivos passam; e um oráculo deliberadamente com leakage "posting a Sharpe ratio of 35 survives standard statistical corrections", mostrando que guardrails contra look-ahead não são redundantes com a correcção estatística — [IDEAS/RePEc 2608.27734](https://ideas.repec.org/p/arx/papers/2608.27734.html); [arXiv 2608.27734](https://arxiv.org/pdf/2608.27734).

### Inferences
- Para o bot: registar N = número de variantes de prompt, modelo Ollama, temperatura, limiares de confiança e parâmetros de bracket já experimentados; calcular DSR com esse N sobre a série diária de P&L paper. Se DSR < 0,95, não escalar risco.
- Exemplo ilustrativo da fórmula MinBTL (cálculo próprio): N = 10 tentativas, E[max SR] ≈ 1,0 anualizado → MinBTL ≈ 2·ln(10)/1 ≈ 4,6 anos de dados; com N = 3 → ≈ 2,2 anos. Para dados intradiários o T em barras é grande, mas o Sharpe deve ser calculado em retornos diários agregados para que a fórmula faça sentido.
- A combinação recomendável antes de escalar: (1) hit-rate > baseline permutado (p < 0,05); (2) Brier < Brier climatológico; (3) PSR(0) > 0,95 sobre retornos diários; (4) DSR com N honesto > 0,95; (5) WFE > 0,5 nas janelas walk-forward; (6) Monte Carlo com ruína < 5 % ao nível de risco previsto.

### Gaps
- Não foi possível ler os papers originais (SSRN/arXiv bloqueados); as fórmulas vêm de Wikipedia/implementações e são consistentes entre si, mas o leitor deve confirmar no original.
- Não se encontraram recomendações numéricas de López de Prado específicas para dados de 1 minuto.

## Q6. Pitfalls de look-ahead e sobrevivência específicos de LLMs (contaminação do treino com preços/notícias históricos)

### Takeaway
A literatura de 2025-2026 trata a contaminação temporal como o maior problema do backtesting com LLMs: o modelo "conhece" o período testado através dos pesos, mesmo sem ver dados futuros no prompt. Consequências medidas: quedas de desempenho de > 50 % após o cutoff de treino (FinMem, QuantAgent), e um teste estatístico (Lookahead Propensity) mostra que a precisão do LLM é amplificada exactamente nos pares empresa-data que o modelo memorizou. Mitigações: backtestar apenas após o cutoff do modelo, usar modelos cronologicamente consistentes (ChronoBERT/ChronoGPT), anonimizar tickers/datas, e preferir avaliação forward (paper) à retrospectiva.

### Cited Findings
- "If an agent is backtested on data from 2023 but the underlying model was trained on data up to 2024, the model already 'knows' what happened. This is called temporal contamination"; "the performance of models like FinMem and QuantAgent drops significantly — by over 50% in some cases — when tested on data that falls after their training cutoff" — [Moclaw: What is TradingAgents](https://moclaw.ai/blog/what-is-tradingagents) (blog secundário que resume "The Alpha Illusion").
- Issue #805 do TradingAgents (11 Mai 2026), "Temporal Knowledge Leakage in LLM Backtesting (Model-Level Future Information Contamination)": a framework evita exposição explícita a dados futuros com fetching date-aware, mas um LLM treinado em 2026 a backtestar 2023 já codifica NVDA/boom de IA, FTX, SVB; pergunta se se devem usar checkpoints antigos ou "temporal purity protocols"; sem resposta dos mantenedores à data — [GitHub TradingAgents issue 805](https://github.com/TauricResearch/TradingAgents/issues/805).
- "Detecting Lookahead Bias in LLM Forecasts" (Gao, Jiang, Yan, 2026): define Lookahead Propensity (LAP) via consulta de recordação só com a data para um par empresa-data; "LAP is materially positive throughout the in-sample period and collapses essentially to zero right after the training-data cutoff"; em duas tarefas (manchetes → retornos; transcrições de earnings calls → capex) "the LLM forecast's predictive power is amplified on high-LAP firm-date pairs, and the interaction loses significance on post-training-cutoff samples" — [arXiv 2512.23847](https://arxiv.org/abs/2512.23847); slides em [ABFER 2026](https://abfer.org/media/abfer-events-2026/annual-conference/slides-tech-ai/260518-AI-A-Test-of-Lookahead-Bias-in-LLM-Forecasts.pdf).
- "Does Training on Future Data Pay? Look-Ahead Bias in Forecasting with Pretrained Models" (Chen et al., Set 2026) avalia cinco famílias de modelos de séries temporais em 14 mercados de acções e quatro horizontes para medir se informação pós-origem infla a precisão e o valor económico — [arXiv 2609.20554](https://arxiv.org/pdf/2609.20554) (resumo via pesquisa).
- ChronoBERT/ChronoGPT: LLMs "chronologically consistent" treinados apenas com texto até cada data, para preservar validade de testes económicos sem leakage — [arXiv 2502.21206](https://arxiv.org/html/2502.21206v3).
- "Profit Mirage: Revisiting Information Leakage in LLM-based Financial Agents" e "Time Travel is Cheating: Going Live with DeepFund for Real-Time Fund Investment Benchmarking" (benchmark em tempo real para evitar leakage) — [alphaxiv 2510.07920](https://www.alphaxiv.org/abs/2510.07920.md); [arXiv 2505.11065](https://arxiv.org/html/2505.11065v2) (títulos/resumos via pesquisa).
- Sistemas como FinMem/FinAgent "lack multiple-testing correction indexed to the search's trial count, and never demonstrate that their execution environments make lookahead impossible rather than merely discouraged" — [arXiv 2608.27734](https://arxiv.org/pdf/2608.27734).
- "The Alpha Illusion": a evidência pública "cannot yet distinguish robust predictive ability from temporal contamination, unmodeled frictions, short-window Sharpe uncertainty, narrative fitting, and parametric priors"; TradingAgents passou de Sharpe 0,43 (bruto) para 0,22 após custos — [alphaxiv 2605.16895](https://www.alphaxiv.org/abs/2605.16895); [Moclaw](https://moclaw.ai/blog/what-is-tradingagents).
- TradingAgents v0.3.1 adicionou filtragem de look-ahead nos dados Alpha Vantage ("point-in-time data integrity") — [GitHub TauricResearch/TradingAgents](https://github.com/TauricResearch/TradingAgents).

### Inferences
- Para o bot local: qualquer backtest em datas anteriores ao cutoff do modelo Ollama é suspeito, mesmo que o prompt só contenha indicadores numéricos — o LLM pode inferir a data/ticker a partir do nível de preço (ex.: AAPL a 180 USD ≈ 2023-2024). Mitigação prática: (a) remover ticker e datas do prompt, normalizar preços (retornos/z-scores em vez de níveis), (b) só aceitar como evidência o período posterior ao cutoff do modelo e o paper trading forward, (c) comparar desempenho pré vs. pós-cutoff como teste de contaminação (análogo ao LAP).
- Viés de sobrevivência clássico é menor com 2-5 acções fixas, mas existe uma versão LLM: as acções foram escolhidas porque são famosas/bem-sucedidas, e o LLM tem priors narrativos fortes sobre elas ("NVDA sobe"); testar também em tickers menos mediáticos ou com rótulos anonimizados.

### Gaps
- Nenhum paper encontrado quantifica contaminação temporal para decisões intradiárias de 1 minuto (todos usam frequência diária ou inferior); a magnitude do efeito a 1 min é desconhecida.
- Não foi possível ler os PDFs completos de 2605.16895, 2608.27734, 2512.23847 (apenas resumos e espelhos).

## Q7. Repos que demonstram backtests com LLM-in-the-loop (TradingAgents, FinMem, ai-hedge-fund) e caveats documentados

### Takeaway
Os três repos mais populares correm backtests diários (não intradiários), com dados de APIs externas, e os seus caveats documentados limitam-se a "só para investigação/educação"; o único reconhecimento explícito de leakage ao nível do modelo está numa issue aberta do TradingAgents, não na documentação. Nenhum fornece um harness de 1 minuto reutilizável.

### Cited Findings
- **virattt/ai-hedge-fund**: 63,9k estrelas; MIT; 937 commits, 122 PRs e 55 issues abertas; agentes (Market Data, Quantitative, Fundamentals, Sentiment, Risk, Portfolio); dados via "Financial Datasets API"; fornecedores LLM Anthropic, OpenAI, DeepSeek, Google, xAI, Kimi (Ollama suportado segundo descrições de terceiros); backtester "replay[s] a fund over history" em dias de mercado reais (daily); comando `poetry run python src/backtester.py --ticker AAPL,MSFT,NVDA`; disclaimer: "for educational and research purposes only … Not intended for real trading or investment" — [GitHub virattt/ai-hedge-fund](https://github.com/virattt/ai-hedge-fund); [SourcePulse ai-hedge-fund](https://www.sourcepulse.org/projects/1797841).
- **TauricResearch/TradingAgents**: 109,8k estrelas; Apache-2.0; v0.6.0 (Out 2026) com relatórios HTML, fornecedores por tier de modelo e "parallel decision settlement"; agentes analistas (fundamentals, sentiment, news, technical) + investigadores bull/bear + trader + risco + gestor de carteira; dados SEC EDGAR (point-in-time), Yahoo Finance, FRED, StockTwits, Reddit, Alpha Vantage; `llm_provider: 'ollama'` com `http://localhost:11434/v1` e endpoints OpenAI-compatible (vLLM, LM Studio, llama.cpp); `run_backtest` avalia decisões numa grelha ticker × data "scoring realized alpha against regional benchmarks and tracking performance by rating category"; caveat: "designed for research purposes … not intended as financial, investment, or trading advice", desempenho varia com modelo, temperatura e qualidade de dados — [GitHub TauricResearch/TradingAgents](https://github.com/TauricResearch/TradingAgents).
- **pipiku915/FinMem-LLM-StockTrading**: 962 estrelas; MIT; paper arXiv:2311.13743; dados em pickle; modos "train" e "test" com checkpoints; exemplo TSLA 2022-06-30 a 2022-10-11; GPT-4 ou modelos HF via TGI, embeddings text-embedding-ada-002 obrigatórios; a página "does not explicitly document look-ahead bias or data leakage concerns" — [GitHub pipiku915/FinMem-LLM-StockTrading](https://github.com/pipiku915/FinMem-LLM-StockTrading).
- Benchmark de capacidade de LLMs para escrever backtests (não de trading): "BacktestBench" — [arXiv 2605.17937](https://arxiv.org/pdf/2605.17937) (título apenas).
- Avaliação crítica agregada: "The Alpha Illusion" cobre FinCon, FinMem, TradingAgents, FinAgent, QuantAgent e FLAG-Trader e conclui que o alpha reportado "should not be treated as deployment evidence" — [alphaxiv 2605.16895](https://www.alphaxiv.org/abs/2605.16895); resumo em [Harbourfront Quant](https://harbourfrontquant.substack.com/p/how-effective-are-llm-trading-agents).

### Inferences
- O que se pode reutilizar destes repos é o padrão arquitectural (decisão do LLM → módulo de risco independente → execução) e a grelha ticker × data do `run_backtest` do TradingAgents; nenhum resolve latência por barra nem cache de decisões para 1 min.
- O facto de o repo com 109k estrelas ter uma issue de leakage ao nível do modelo sem resposta indica que a comunidade ainda não tem um protocolo padrão; o bot deve documentar o seu próprio ("cutoff do modelo", "período de avaliação", "N tentativas").

### Gaps
- Não foi possível ler `src/backtester.py` do ai-hedge-fund nem o código de `run_backtest` do TradingAgents para confirmar como tratam custos, slippage e look-ahead.
